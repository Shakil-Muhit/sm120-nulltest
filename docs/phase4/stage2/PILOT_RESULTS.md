# Stage-2 pilot results (engineering evidence; ml-beast GPU 4, RTX 5090 GPU-eb6e4a8a…, driver 595.84, pinned venv torch 2.8.0+cu128 / triton 3.4.0; shared host — other users' jobs on GPUs 0–3, an idle API server holding 714 MiB on GPU 4)

These results are separate from the Stage-1 pod evidence: directional, unregistered protocol (`--no-manifest`, 2×50 repeats where matched), never paired with pod numbers, never a headline. Probe cards: `PROBES.md`; raw outputs: `results/`.

## B1 — GEMM operand locality after cast removal (candidate 1) — SUPPORTS the warming mechanism
`results/probe_b1_gemm_locality_4410.json`. 300 `nn.Linear` calls per 100 ms forward, 88 distinct shapes; each shape timed 100× per condition from a cold L2 (256 MB flush before every iteration), GEMM-only CUDA-event time (≈ 2 µs quantization), launch-weighted per pass:

| condition | GEMM-only µs per pass | vs (a) |
|---|---|---|
| (a) fp32 weight, cast kernel then GEMM | 2,650 | — |
| (b) pre-cast fp16 weight, GEMM alone | 3,100 | +450 |
| (c) pre-cast weight, read-touch of the weight then GEMM | 2,422 | −228 |
| (d) pre-cast weight, cast of an unrelated same-size tensor then GEMM | 2,931 | +281 |

Kernel names identical between (a) and (b) for all 88 shapes (`cutlass_80_wmma_tensorop_f16_s161616gemm` family for 258 of the 300 calls). Dominant shape (M = 11, N = K = 1,536, 60 calls, 4.7 MB weight): a 12.3, b 14.3, c 10.2, d 14.3 µs. Reading: warming the operand (writing or reading it) reproduces the in-model excess (session 4: +374 µs; session 3 pre-cast: +352 µs) and more; the unrelated-cast control contrast (b − d = 169 µs) is consistent with operand-specific warming for most of the 450 µs; condition-specific clocks were not recorded, so a generic preceding-kernel component is bounded only by that contrast, not established. L2 residency and translation locality are not separated (a read-touch warms both). Qualifications: idle-clock regime between synchronized iterations (the unrelated-cast condition controls for wake-up); event quantization; isolation rather than graph replay.

## C0 — band layout and pad-and-batch waste (candidate 3) — analysis only
`results/probe_c0_band_layout.json`. Pinned config: 60 bands, widths 6 … 130 bins (sum 1,979; `freq_indices` has 3,958 entries because the stereo channel doubling is applied to the indices; the complex factor is applied separately, so each band projection's input width is 4 × band width), `dim_freqs_in` 1,025. Pad-and-batch work = 3.94 × useful (74.6 % padding), a fraction independent of the number of frames — so padding waste alone cannot produce a length-dependent ranking flip; a regime change (per-launch floors amortized at large M) is required, which the session-4 per-frame GEMM efficiencies show (C3 114 → 20.6 µs/frame, HG 76 → 21.4 µs/frame from 11 to 801 frames).

## A1 — recompile-limit intervention (candidate 2)
`results/matched_C1_C1_c352800_lim{8,64}.json`. **A/A form (C1 vs C1#2, one process):** at the default limit 8, block medians 36.75 / 36.95 ms (C1 − C1#2 = −0.137 ms), torch logs show only the standard `[3/8]` (einops `rearrange`) hit — no `Attention.forward` exhaustion, no gap; at limit 64: −0.249 ms, no hits at all. Reading: with identical compile options, the second instance's guards pass on the first instance's cache entries, so the shared per-code-object budget is not exhausted — the artefact needs two builds whose entries invalidate each other (the pod's C1 vs C1P pairs, different Inductor options). **Discriminating form (C1 vs C1P, limits 8 vs 64):** `results/matched_C1_C1P_c352800_lim{8,64}.json`, `results/run_probe_a1b.log`. At the default limit 8 the pod artefact is reproduced on ml-beast: C1 (built first) 36.67 / 36.99 ms, C1P (built second) 51.49 / 51.67 ms, C1 − C1P = **−14.75 ms**, torch logs show both `[3/8]` (einops `rearrange`) and `[7/8]` (`Attention.forward`, mel_band_roformer.py:127) limit hits. With `torch._dynamo.config.recompile_limit = 64` (same pair, same process structure): C1 36.70 / 37.11 ms, C1P 37.04 / 37.21 ms, C1 − C1P = **−0.22 ms**, and **no** limit hit at all. Reading: the intervention removes the 14.5 ms artefact — the recompile-limit fallback of the second build is its cause, not an accompanying symptom; C1P built second under a sufficient budget runs within 0.2 ms of C1 (engineering-grade timing; a 14.5 ms effect against ≈ 0.2 ms of noise). This is causal confirmation on the engineering host; the registered pod protocol has not run the intervention.
