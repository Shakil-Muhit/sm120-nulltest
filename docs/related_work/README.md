## Positioning paragraphs

**Graph deployment and execution optimization (F1, F2, F5, F6, F7).** The effect this study measures is established: compiled and graphed inference is faster than eager by the documented 1.5–2.3×, graph breaks cost real time (GraphMend), per-replay copies are a known first-order cost (PyGraph; NVIDIA), and one full graph beats segmented and piecewise variants (SGLang). What was not found in the sources reviewed is the accounting: a per-pass decomposition of a reduce-overhead forward into staging copies, lost fusion, idle between graph launches and kernel selection, a cause class made of incidental Python rather than control flow, per-node stream, graph and PDL-graph costs on SM120, and a priced autocast re-cast term that moves from 3 % to 37 % between operating points. The megakernel literature (Cohere, MPK, Hazy) sets the terms for F5c and F6: the study's X12 is a boundary-removal figure with the excluded mechanisms enumerated, and F6 is a statement about when boundary removal pays, with achieved bandwidth named as the other lever.

**Performance diagnosis and prediction (ledger, F8 headroom, profiler perturbation).** The ledger's estimator is GPA's S = T/(T − M) applied per kernel class, and its validation bar is Daydream's and GPA's estimated-versus-achieved table. The study adds bookkeeping, not a method: confidence grades, stacking groups that bound how rows combine, a realized/ceiling column filled after intervention, a coverage check that any realized value above its ceiling falsifies the row's attribution, and unprofiled primary timings with the profiler perturbation reported as its own result (node-level trace ratio 1.052 for C3 at 100 ms; `LEDGER.md` caveats). TaxBreak shows what the ISPASS genre accepts (decompose, then recommend) on the host side in eager mode; this study works on the device side under graph replay and scores its recommendations.

**Band-split workloads and ragged GEMMs (F3, F4, F8, SM120).** Grouped-GEMM work is ragged along M with fixed K; MelBandRoformer's band split is ragged along K with fixed M, and torch 2.8.0 gates the grouped path to compute capability 9.0 while its 2D×2D mode would express ragged K. The pad-and-batch result is therefore a measured comparison in this shape regime (−1.7 % at 8 s, +40 % at 100 ms, with the decomposition into batching, padding, efficiency and non-GEMM terms), not an absence claim. On SM120 itself, Jarmusch et al. establish the instruction set (no wgmma, no tcgen05 on GB203); the study's characterization is at the framework level (realized rates by accumulator through cuBLAS/Triton under PyTorch 2.8, SDPA backend behaviour, feature gating, launch/PDL slopes) and is stated as not found in the sources reviewed for the RTX 5090.

**Measurement methodology.** Warmup, synchronization, event timing, restarts and per-level repetition are standard (PyTorch recipe, CUDA best practices, Kalibera–Jones). The study's unusual elements have adjacent precedent rather than a venue track: self-registration with public time evidence (Chen's preregistered A/B; registered reports in software engineering), a planted-fault validator, a trace gate on graph identity, and an agent review gate with its reliability disclosed. The exposed flank named by the sweep, intervals, is now covered by block-level bootstrap intervals on every headline and matched pair and by the E6 A/A block with five additional restarts; the time evidence is client-side until the repository is public or the owner obtains the GitHub Events record (`docs/provenance/push_evidence.md`).
